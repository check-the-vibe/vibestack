## Outcome and scope

Fix the observed Codespaces resume failure without teaching privileged bootstrap
to trust state owned by the desktop user. Isolate runtime data in a persistent
Dev Container named volume outside `/workspaces`; keep source shared at
`/projects/vibestack`. Preserve existing state through an explicit, checked
migration and retain the original directory. Use non-sensitive readiness for
the outer startup probe and fixed local setup access for component restoration.

## Acceptance

- [ ] Fresh Codespaces startup reaches private service health with API auth enabled.
- [x] Existing state is preserved; source ownership and the shared mount are unchanged.
- [ ] Stop/resume retains root-private ownership, credentials and installed state.
- [x] Wrong/missing mounts fail safely; no recursive ownership repair or new public port.
- [ ] Source, disposable image, real Codespaces and parent MCP gateway checks are recorded.

## Evidence and decisions

During VST-011 verification, Supreme Space Parakeet resumed with its existing
auth directory and four SSH host-key files owned by UID 1000 instead of UID 0.
Bootstrap refused that state. Modes remained 0700/0600/0644; no password hash was
present and no secret contents were read. `/data` was restored to 0:1000 by
bootstrap before it stopped. Existing source was clean, with the correct bind.
The platform operation causing the ownership change has not been established;
the observed state is the evidence, not an assumption about GitHub internals.

Source review also found two unauthenticated probes after VST-005: the Codespaces
helper's `/api/v1/status` check and the launcher's `/setup/api/state` restoration
probe. These must use public process readiness and the fixed internal setup
listener respectively. No API authentication exception will be introduced.
